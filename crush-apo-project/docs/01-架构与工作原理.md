# 架构与工作原理

## 一、apo-optimizer：Crush 插件（Skill）

### 文件

| 文件 | 作用 |
|---|---|
| `SKILL.md` | 插件声明（frontmatter 含 name/description）+ 触发条件 + 执行步骤 |
| `scripts/run_apo.py` | 启动器：后台拉起 APO 循环，立即返回，不阻塞 Crush 界面 |

### 触发条件（SKILL.md 约定）

仅当用户**明确**说出以下指令时激活，日常写代码时绝不触发：

- "跑一下 APO"
- "优化提示词"
- "自动优化提示词"

### 触发后 Crush 要做的事（SKILL.md 中的步骤）

1. 向用户展示："正在为您启动 APO 后台进化任务..."
2. 调用 `python $HOME/.config/crush/skills/apo-optimizer/scripts/run_apo.py`
3. 脚本瞬间返回（任务已在后台运行）
4. 立即告诉用户："优化任务已在后台启动，请等待 1-3 分钟后，自行查看 `apo/best_prompt.md` 中的结果。"

### run_apo.py 的工作机制

```python
apo_script_path = ~/apo/apo_loop.py        # 核心脚本路径（按约定放在用户主目录下）
log_file = ~/apo/logs/crush_bg_时间戳.log   # 每次启动新建一个日志文件
subprocess.Popen([python, apo_script_path],
                 stdout=log_file, stderr=STDOUT,   # 脱离前台、后台运行
                 start_new_session=True)            # POSIX 下脱离会话，避免随父进程退出被杀
print("✅ APO 优化任务已成功在后台启动！")            # 立刻返回给 Crush
```

要点：
- 用 `subprocess.Popen` **不等待**子进程结束，所以 Crush 界面秒回；
- `start_new_session=True` 让子进程在 POSIX 系统上脱离当前会话（Windows 上该参数被忽略，行为不变）；
- 找不到 `~/apo/apo_loop.py` 时打印错误并以**退出码 1** 结束，方便上层感知失败；
- 全部输出重定向到 `apo/logs/crush_bg_*.log`（这就是引擎目录里 `crush_bg_` 前缀日志的来源）；
- **路径约定**为 `~/apo/apo_loop.py`，所以引擎必须放在用户主目录的 `apo/` 文件夹里插件才能工作（详见安装文档）。

## 二、apo：APO 核心引擎

核心是单文件脚本 `apo/apo_loop.py`，无外部模块拆分。整个优化循环由**四个角色**构成，
全部由同一个 LLM（智谱 GLM，模型 `GLM-5.3-Flash`，端点硬编码在 `apo_loop.py` 顶部）扮演：

> 引擎所有文件路径都以**脚本自身所在目录**（`SCRIPT_DIR`）为基准解析，
> 因此在任意工作目录下运行 `python apo/apo_loop.py` 都能正确定位配置与产物。

### 角色 1：代码生成器（`run_agent_with_prompt`）

- 把**被测提示词**作为 system prompt，任务需求作为 user message，让模型生成完整 Python 程序。
- `temperature=0.7`。

### 角色 2：硬校验（`hard_check`）

- 纯字符串匹配，检测输出中是否含危险操作：
  - "删除系统目录"、"格式化磁盘"、`rm -rf /`
- 命中任意一条 → **一票否决，该任务直接 0 分**。

### 角色 3：LLM 评分员（`llm_judge`）

- 按三个维度打 0-10 分，权重文案**由 `config.yaml` 的 `weights` 动态生成**（默认：启动 40% / 功能 30% / 交付 30%），与实际加权计算共用同一份配置，不会脱节。
- 要求返回严格 JSON（`response_format={"type": "json_object"}`，temperature=0.1）：
  ```json
  {"startup": 0-10, "requirement_match": 0-10, "delivery_completeness": 0-10,
   "safety_veto": false, "reason": "简短理由"}
  ```
- JSON 解析失败 → 视为 `safety_veto=True` → 该任务 0 分（容错很严格）。
- 解析成功但**缺字段 / 字段是字符串数字**时自动兜底为 0 并转 `float`，不会崩溃。
- 加权得分：`startup*0.4 + requirement_match*0.3 + delivery_completeness*0.3) / 10 * 100`，
  硬校验或 `safety_veto` 任一命中直接 0 分。

### 角色 4：提示词优化器（`optimize_prompt`）

- 输入：当前最佳提示词 + **失败摘要**（所有得分 < 70 的任务及其失败原因）。
- 要求：只改提示词、针对失败原因改进、直接给新版，不要解释。
- 返回值经 `strip_code_fence` 清洗：剥掉 LLM 误输出的首尾 Markdown 代码围栏，
  避免围栏被写进 `best_prompt.md` 并随提示词传给下游。

### 主控制流（`main`）

```
for 每一轮 (max_rounds，默认 3):
    1. backup_before_round  → 备份当前 best_prompt.md + config.yaml 到 backups/round_N_时间戳/
    2. evaluate_prompt      → 用候选提示词在 dev_tasks（d1-d3）上逐任务评估
    3. log_round            → 写日志 logs/round_N_时间戳.log（提示词、平均分、各任务得分）
    4. 平均分 > 历史最佳？
        是 → 覆盖 best_prompt.md，更新最佳提示词
        否 → 丢弃候选，保留原版
    5. 若不是最后一轮 → 调用优化器生成下一轮候选提示词
最后一轮结束：
    用 holdout_tasks（h1，留出集）验收最佳提示词，打印最终报告
```

### 预算控制

- `max_llm_calls`（默认 100）按 **LLM 调用次数**计，生成 / 打分 / 优化三种调用统一计数。
- 超限抛 `BudgetExceeded` 立即停止。
- 粗算：每轮 ≈ dev任务数×2 + 1 次优化调用，最后加留出集任务数×2。
  当前 3 个 dev 任务 + 1 个 holdout，3 轮约 **22 次调用**。
